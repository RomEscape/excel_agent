# Excel Live 시연 대본

**모두 실측으로 검증한 명령만 적는다.** 지어낸 명령은 한 줄도 없다.

- 시나리오 팩: `datasets/excel_demo_scenarios_v1.json`
- 플래너 `ax7bplanner-v3:latest`, 2026-08-11 실측

**두 엔진 모두에서 검증했다.** 실행 환경에 따라 서로 다른 구현이 돌기 때문이다
(`EXCEL_LIVE_ENGINE=auto`는 엑셀에 열린 문서가 있으면 xlwings, 없으면 file을 고른다).
시연은 엑셀을 띄워 놓고 하므로 **아래쪽 xlwings 결과가 시연에 해당하는 수치**다.

| 엔진 | 구현 | 하네스 | 결과 |
|---|---|---|---|
| file (openpyxl) | `excel_live_file_service.py` | `verify_excel_complex_scenarios.py` | 3대본 3/3 (`logs/demo_file_after.json`) |
| **xlwings (COM)** | `excel_live_service.py` | `verify_demo_on_excel_com.py` | **3회 × 3대본 9/9** (`logs/demo_com_final1~3.json`) |

```bash
cd python-sidecar

# 파일 엔진 (엑셀 없이, CI/빠른 확인용)
uv run python scripts/verify_excel_complex_scenarios.py \
  --scenario-pack ../datasets/excel_demo_scenarios_v1.json \
  --artifact-dir ../logs/demo_artifacts

# COM 엔진 (실제 시연 조건 — 워크북을 엑셀에 띄운 채로 돌린다)
uv run python scripts/verify_demo_on_excel_com.py
```

파일 엔진 통과가 COM 통과를 보증하지 않는다. 서로 다른 파일의 다른 구현이라,
한쪽만 재고 "된다"고 말하면 시연장에서 처음 실패를 본다.

---

## 왜 이 문서가 따로 필요한가

기존 진단 배터리(`tests/excel_e2e/command_battery.py`)는 **케이스마다 새 워크북**을
만든다. 명령 하나하나가 되는지는 알려주지만, **명령을 이어서 쳤을 때 결과물이
제대로 쌓이는지는 검증하지 않는다.** 시연은 후자다. 이 대본은 한 통합문서·한
세션에서 턴을 이어 붙여 실제로 돌려 본 결과다.

---

## 대본 A — 월간 매출 보고서 (6턴, 약 17초)

빈손에서 시작해 "정리 → 정렬 → 강조 → 서식 → 집계 → 저장"으로 보고서 하나를 완성한다.

**준비**: `월 / 카테고리 / 수량 / 단가 / 금액 / 상태 / 담당자 / 코드` 8열짜리 표.
데이터 8행이고 그중 `A007` 코드가 중복 1건 있다. (시드 정의: `verify_excel_complex_scenarios.py:68`)

| # | 명령 | 실행된 액션 | 소요 | 이 턴에서 화면이 바뀌는 것 |
|---|------|-------------|------|---------------------------|
| 1 | `코드 열 기준으로 중복 제거해줘` | `dedupe_rows` | 5.7s | 8행 → 7행 (중복 A007 1건 제거) |
| 2 | `금액 열 기준 내림차순으로 정렬해줘` | `sort_range` | 3.2s | 1440 → 840 순으로 재배열 |
| 3 | `금액이 1000 미만인 건은 노란색으로 표시해줘` | `highlight_by_condition` | 3.3s | 990·880·840 세 칸만 노란색 |
| 4 | `A1:H1에 테두리 넣어줘` | `apply_border` | **0.3s** | 머리글 행에 테두리 |
| 5 | `카테고리별 금액 합계를 집계해서 카테고리요약 시트에 만들어줘` | `pivot_table` | 4.0s | `카테고리요약` 시트 생성 |
| 6 | `저장해줘` | `save_workbook` | **0.3s** | 저장 |

**결과 검증** (하네스가 결과 파일을 직접 열어 확인):

- 매출 시트 7행 (중복 제거됨)
- 금액 열 내림차순 정렬 상태
- A1 테두리 있음
- `카테고리요약` 시트 존재, 값 **A=3010 / B=3310 / C=1000** — 원본 합계와 일치

### 시연 포인트

4번·6번이 **0.3초**인 이유를 짚으면 좋다. 이 둘은 규칙이 문장을 바로 알아들어
LLM을 아예 호출하지 않는 경로(quick rule)다. 나머지는 로컬 LLM이 계획을 세운다.
"전부 LLM에 맡기지 않고, 확실한 건 규칙으로 즉답한다"는 설계가 속도 차이로 보인다.

## 대본 B — 되묻기로 빈칸 채우기 (3턴, 약 1초)

정보가 모자라면 지어내지 않고 **되묻는다**는 걸 보여 준다.

| # | 명령 | 응답 |
|---|------|------|
| 1 | `정산 시트 만들어줘` | 시트 생성 |
| 2 | `표 만들어줘` | **되묻기** — "표 크기와 헤더를 알려주세요. 예: 5*5 또는 4행 3열, 금액, 장소, 날짜, 요건, 비고" |

## 절대 시연하지 말 것

실측에서 **결과가 틀리게 나오는** 명령들이다. 되묻지 않고 자신 있게 틀린 답을 내므로
시연에서 가장 위험하다. (근거: `logs/diagnostics/0811-204214-after-task7.report.json`,
관측 케이스 5건 3회 반복 전부 오라클 불일치)

| 명령 유형 | 실제로 일어난 일 |
|-----------|------------------|
| `지역이 비어 있는 행은 삭제해줘` | 멀쩡한 행까지 46행 삭제 |
| `지역이 비어 있는 칸은 '미상'으로 채워줘` | 정작 빈칸 3개는 안 채움 |
| `금액에 유난히 큰 이상치가 있으면 빨간색으로 표시해줘` | 이상치는 2개인데 49행을 칠함 |
| `금액이 비정상적으로 큰 이상치 행은 삭제해줘` | 멀쩡한 행 대량 삭제 |
| `수량 열에 문자열로 들어간 숫자를 숫자로 바꿔줘` | 3회 모두 되묻기만 하고 못 함 |

공통점은 **"데이터 상태를 먼저 봐야 아는" 명령**이다. 모델이 표를 실제로 읽지 않고
계획을 세우기 때문에, 화면에 40행까지만 보이면 그 아래는 없는 셈 친다.

`정렬해줘`처럼 대상이 빠진 문장도 시연에는 부적합하다. 되물을 때도 있고 알아서
열을 골라 실행할 때도 있어 **매번 같게 나오지 않는다**(대본 B 초기 버전에서 확인).

## 알려진 함정

### 1. ~~표 만들기는 반드시 빈 시트를 열어 둔 상태에서~~ — 2026-08-11 수정됨

되묻기 다음 턴에서 문장이 지목한 시트를 잃고 **활성 시트를 덮어쓰던 버그**가 있었다.
지금은 고쳤고 회귀 시나리오(`regress-slot-keeps-named-sheet`)로 못을 박아 뒀다.

수정 전후를 같은 시나리오·같은 COM 경로에서 비교하면 이랬다. 평가 시트에 데이터를
둔 채 문장으로만 정산을 지목한 경우다.

| 검증 | 수정 전 | 수정 후 |
|---|---|---|
| `정산!A1:C1` 머리글 | 빈칸 — 표가 정산에 안 감 | 이름·점수·등급 |
| `평가!A2` (민수) | **None — 삭제됨** | 민수 |
| `평가!A3` (지은) | **None — 삭제됨** | 지은 |
| `평가!C1` | **`등급`으로 덮임** | 결과 |

원인은 슬롯이 활성 시트만 들고 있었던 것이다. `PendingCreateTableSlots.sheet_name`은
매 턴 `req.sheet_name`(=활성 시트)으로 덮이는데, 문장에서 지목한 시트를 담을 자리가
따로 없어 `_build_create_table_steps`가 `sheet_name` 없는 계획을 냈고, 하류가 그걸
활성 시트로 떨어뜨렸다. `explicit_sheet_name`을 따로 두고 모든 단계에 박아 준다.

`이 시트에`·`새 시트에` 같은 지시어는 이름으로 치지 않는다(`_named_sheet_in_text`).
그러지 않으면 없는 시트를 찾아 되묻는다.

### 2. 표 생성은 기존 데이터를 밀어내지 않고 덮어쓴다

`N행 M열 표`는 A1부터 그 크기만큼 **덮어쓴다**. 빈 시트에서만 쓴다.

### 3. 통합문서는 절대경로로만 찾는다

`_find_workbook`은 후보 문자열을 워크북의 `fullname`(절대경로)과 **문자열로** 비교한다.
상대경로를 넘기면 엑셀에 버젓이 열려 있는데도 "통합문서를 찾을 수 없습니다"가 난다.
COM 하네스 첫 실행에서 6턴 전부 이 이유로 실패했다. 앱은 `list_workbooks`가 준
경로를 그대로 돌려주므로 정상 흐름에서는 문제가 없지만, 스크립트로 부를 때는 주의한다.

### 4. 엑셀 인스턴스는 하나만 띄워 두고 시연한다

`_find_workbook`은 `self._app().books`, 즉 **인스턴스 하나만** 훑는다. 다른 엑셀
인스턴스에 열린 워크북은 못 찾는다. 시연 전에 `Get-Process EXCEL`로 떠 있는 게
없는지 확인하고 시작하는 편이 안전하다.
